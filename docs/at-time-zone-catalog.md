# Catalog-wide `AT TIME ZONE` reference

The [capture script](../scripts/capture-at-time-zone-catalog.mjs) queried the pinned SQL Server 2025 image used by the focused [AT TIME ZONE reference](at-time-zone.md). Its [raw fixture](../reference/at-time-zone-catalog.json) retains the image digest, `@@VERSION` (RTM-CU7, build 17.0.4065.4 on Linux), the `sys.time_zone_info` name result, and eight ordered conversion results. Every conversion returned one row for each of the 141 exposed Windows zone names, with no errors in this capture. The `name` column was reported as `NVarChar` length 256 with flags 8; the converted `value` columns were `DateTimeOffset` scale 7 with flags 1. All rows, descriptors, messages, errors, and completion events remain in the fixture.

Seven probes interpret a `DATETIME2(7)` wall time in each zone: January 1900, July 1970, January 2000, January and July 2024, January 2030, and July 2050. The eighth converts one UTC `DATETIMEOFFSET(7)` instant into every zone. Each row includes SQL Server's string rendering and `DATEPART(TZOFFSET, value)` because Tedious decodes the `datetimeoffset` value as a UTC JavaScript `Date`, which alone loses the displayed offset.

The selected dates expose several adapter requirements in this image. Twenty-two zones have different offsets at the January 1900 and January 2024 probes; 40 differ between the January and July 2024 probes. Twelve have a non-hour offset in January 2024. `Paraguay Standard Time` reports `-04:00` for July 2024 and `-03:00` for July 2050. These are observations at the sampled dates, not a complete historical transition table or a promise about future rule updates.

The separate [transition core](at-time-zone-core.md) accepts explicit UTC transitions. A future effectful adapter must map all supported Windows names to an identified, versioned rule source and obtain transitions for the requested date range. It should compare both local-wall and UTC-instant conversions against these rows, then probe transition boundaries rather than interpolating between these sparse samples. [Microsoft documents that `AT TIME ZONE` depends on external time-zone rules and is nondeterministic](https://learn.microsoft.com/en-us/sql/t-sql/queries/at-time-zone-transact-sql?view=sql-server-ver17). The image digest identifies SQL Server bytes; it does not pin the host rule database across machines or updates. msduck does not yet support this SQL expression.

On a Docker-capable host with Node dependencies, run `node scripts/capture-at-time-zone-catalog.mjs path/to/new.json` to make a new capture; the script refuses to overwrite an existing file. Run `node scripts/capture-at-time-zone-catalog.mjs --check reference/at-time-zone-catalog.json` to check the retained file without starting SQL Server. The check compares source queries, pins this capture's exact ordered 141-name set by SHA-256, and verifies that every conversion covers that set with offset evidence. A new capture may retain a changed catalog for explicit review; compare it with the pinned raw file without normalizing differences.
