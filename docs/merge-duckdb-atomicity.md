# Pinned DuckDB MERGE capability and atomicity probe

`tests/merge_duckdb_atomicity.rs` runs native `MERGE INTO` directly through the Rust `duckdb` dependency in `Cargo.lock` (`duckdb 1.10505.0`, bundled engine `version() = v1.5.5`). It does not pass through `msduck`'s T-SQL parser or server. Each test uses a fresh in-memory database. The first-party SQL Server comparator is [PR #196's exact 46-case fixture](https://github.com/mirek/msduck/blob/ffeb20b86507fc15cabfec4059abc4a06a264fbd/reference/merge-execution.json), captured on SQL Server 2025 `17.0.4065.4`. Only directly comparable cases are called equivalent here.

Run with `cargo test --test merge_duckdb_atomicity --locked -- --nocapture --test-threads=1`. The pinned-library probe first ran on `linux.local` with Rust 1.95.0; it was compiled from this isolated branch by `scripts/remote-build.mjs`, then executed under that workspace's remote lock. The tests assert the material outcomes rather than only printing them. They deliberately do not assert a MERGE `RETURNING` row order.

| Probe | Pinned DuckDB observation | SQL Server comparator and implication |
| --- | --- | --- |
| Mixed matched UPDATE, unmatched INSERT and BY SOURCE DELETE | `RETURNING merge_action,id,n` produced UPDATE `(1,11)`, DELETE `(2,20)`, DELETE `(3,30)` and INSERT `(4,44)`; target ended `(1,11),(4,44)`. | SQL Server's mixed capture produced the same four **action kinds** and final target, with DONE/`@@ROWCOUNT` 4. Its OUTPUT INTO includes old/new images and typed descriptors that DuckDB's RETURNING has not supplied. Native output ordering is not a compatibility promise. |
| Duplicate source rows for target `id=1` | Native MERGE succeeded and updated the target to `n=12` in this Linux run (the test accepts either of the two source values, because source order is not specified). | SQL Server raised 8672 and left `(1,10)`. Native MERGE cannot be exposed directly without a pre-write duplicate-match check. |
| CHECK failure inside explicit transaction | After `BEGIN` and a prior successful `INSERT (9,9)`, MERGE raised `Constraint Error: CHECK constraint failed on table t with expression CHECK((n > 0))`. A following SELECT and INSERT both raised `TransactionContext Error: Current transaction is aborted (please ROLLBACK)`. `COMMIT` returned success but discarded the prior insert; final target was the original `(1,10),(2,20),(3,30)`. | SQL Server's captured 547 failure leaves the MERGE target unchanged. The broader requirement to retain prior writes and keep a recoverable explicit transaction usable needs separate SQL Server captures for this exact sequence, but existing backend recovery tests already show the same DuckDB abort behavior for other runtime errors. Native MERGE cannot provide SQL Server-style statement recovery inside an ambient transaction by itself. |
| Duplicate INSERT violates primary key inside explicit transaction | Native MERGE raised `Constraint Error: PRIMARY KEY or UNIQUE constraint violation: duplicate key "4"`; later SELECT/INSERT raised the same aborted-transaction error. ROLLBACK removed the earlier `(9,9)` insert. | Constraint translation alone cannot restore statement-local effects or the prior transaction state. |
| CHECK failure outside explicit transaction | The MERGE failed and the target stayed at its original three rows. | Native one-statement atomicity is useful for autocommit MERGE, but it does not solve the ambient-transaction gap. |
| Successful MERGE inside explicit transaction followed by ROLLBACK | UPDATE `(1,11)` and INSERT `(4,40)` were visible before ROLLBACK; afterward the original three rows returned. | This matches the captured successful MERGE/rollback visibility at the level of target rows; TDS transaction descriptors and counts remain server work. |
| Self-reference | `USING (SELECT id,n+1 FROM t)` succeeded, returning three UPDATE actions. | The SQL Server fixture does not cover self-reference; no compatibility conclusion follows. |
| Physical identity and row images | In the mixed MERGE, `rowid` for updated `id=1` changed from 0 to 3; inserted `id=4` had rowid 4. `RETURNING merge_action, old.n, new.n` failed with `Binder Error: Referenced table "old" not found!` | Do not use backend `rowid` after mutation as a stable SQL Server target identity or assume native RETURNING supplies `deleted`/`inserted` images. Capture pre-write images under a private identity before applying actions. |

The [DuckDB MERGE documentation](https://duckdb.org/docs/stable/sql/statements/merge_into.html) describes the native matched/unmatched arms and `RETURNING merge_action`; the [transaction documentation](https://duckdb.org/docs/current/sql/statements/transactions) describes backend ACID transactions. The probe establishes the narrower behavior above on the exact bundled revision. `tests/backend_transaction_recovery.rs` additionally confirms that runtime errors abort an ambient DuckDB transaction and that `SAVEPOINT` is rejected by its parser. Those are concrete limits, not reasons to silently downgrade SQL Server transaction semantics.

The runtime adapter therefore needs a typed pre-write action plan with SQL Server duplicate detection, logical old/new image capture and metadata, and a write strategy with genuine statement-local rollback inside an existing transaction. A plain native MERGE plus error-number translation is insufficient. Prevalidating known CHECK/unique constraints may prevent some errors but does not prove recovery for conversion, trigger, concurrency or future backend failures. Until a stronger atomicity strategy and differential TDS tests exist, `src/engine.rs` should continue rejecting executable MERGE.
