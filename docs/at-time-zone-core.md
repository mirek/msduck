# Staged `AT TIME ZONE` transition core

The pure resolver in `crates/msduck-core/src/at_time_zone.rs` consumes a caller-owned snapshot: an initial signed-minute offset and strictly increasing UTC transition instants with continuous before/after offsets. It uses the same 100 ns tick epoch as `DateTime2`. It performs no host time-zone lookup and reads no clock or process state. Validation caps snapshots at 100,000 transitions, checks SQL Server's `±14:00` offset and date ranges, and rejects discontinuous, duplicate, unordered, or no-op transitions.

For an offset-aware input, `resolve_utc` preserves the instant and selects the destination offset. For an offset-free input, `resolve_local` treats its fields as local wall time. It selects the earlier UTC occurrence in an overlap, which is the pre-change offset in the observed autumn cases. It advances a nonexistent spring wall time by the transition gap while applying the post-change offset. The tests compare exact UTC ticks, adjusted local ticks, and offsets with the [pinned SQL Server 2025 capture](../reference/at-time-zone.json), including Central European and Pacific transitions and chained conversion. A local lookup binary-searches the UTC transition history and examines only the 28-hour window allowed by the `±14:00` offset bound, so ordinary lookups do not scan the whole history for each SQL row.

This is a staged module, included directly by its integration test until `crates/msduck-core/src/lib.rs` becomes available after another worker's claim. It is not yet linked into the server, and msduck does not yet support the SQL `AT TIME ZONE` expression. Follow-up work must export the module, map Windows zone names to a versioned rule source in an effectful adapter, bind permitted input types and output metadata in `msduck-sql`, and lower the expression through the root execution layer. The pinned image identifies the observed SQL Server behavior; [Microsoft documents the rule source as external and the expression as nondeterministic](https://learn.microsoft.com/en-us/sql/t-sql/queries/at-time-zone-transact-sql?view=sql-server-ver17).

The resolver assumes the supplied snapshot accurately represents the requested zone throughout the relevant date range. Neither its transition limit nor a passing comparison with four example transitions proves full historical Windows-zone compatibility. The adapter must supply and identify the actual rules used for each execution; it must not silently substitute the host's current default zone.
