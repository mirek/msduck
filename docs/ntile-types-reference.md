# NTILE bucket expression types: SQL Server reference

The [pinned SQL Server 2025 capture](../reference/ntile-types.json) contains 29 ordered requests in each of two fresh databases. A second independent container replay matched the retained runs exactly. The [capture script](../scripts/capture-ntile-types.mjs) fixes the request plan, image digest and fixture SHA-256 (`221e5848fbc16740ced1750d47971ffe3803e1687868327b6b400490951b2a06`). It checks rows, column descriptors, full diagnostics, event order and raw DONE status/command words. The source is a three-row `VALUES` relation ordered by `n`, so each bucket outcome is visible without persistent table state.

TINYINT, SMALLINT, INT and BIGINT expressions containing 2 all return buckets 1, 1, 2 with a nullable-family `IntN(8)` result descriptor. A BIGINT count of `9223372036854775807` returns 1, 2, 3. These results show that SQL Server accepts the four tested integer families and retains a BIGINT result independent of bucket expression width.

BIT, DECIMAL(10,2), FLOAT, VARCHAR, NVARCHAR, VARBINARY, DATE and UNIQUEIDENTIFIER expressions all fail at binding with error 4116, state 1, class 15: `The function 'ntile' takes only a positive int or bigint expression as its input.` Numeric-looking character text and an integral decimal value still fail. Typed NULL expressions in TINYINT, BIT, DECIMAL, VARCHAR and DATE fail identically. Each of those batch requests emits ERROR then DONE (status 2, command 253), with no result metadata. This establishes type rejection for those particular expressions; it does not establish diagnostic precedence against unrelated query errors or cover every implicit conversion and correlated expression.

A prepared INT parameter exposes the `IntN(8)` descriptor at prepare. Executions bound to 2 return 1, 1, 2; bindings to NULL and 0 emit the same 4116 diagnostic *after* metadata, with DONEPROC status 2/command 224. The same prepared handle succeeds again when rebound to 2, and unprepare succeeds. Preparing the same statement with DECIMAL(10,2) or VARCHAR(8) parameters instead emits 4116 followed by 8180 (`Statement(s) could not be prepared.`), before any execution. The fixture retains those ordered tokens and the prepared-handle lifecycle.

These are SQL Server observations, not msduck runtime claims. The first-party [NTILE implementation note](ntile.md) describes the current native validator and its remaining compile/wire gaps; draft PR #584 carries a separate NULL-bucket capture. This type matrix guides later binder and diagnostic work without normalizing those differences.
