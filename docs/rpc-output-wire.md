# SQL Server RPC OUTPUT wire evidence

`reference/rpc-output-wire.json` retains nine first-party RPC response captures from the pinned SQL Server 2025 image. The generator ran the same cases in two fresh databases in each of two independent containers. Within each container the complete response bytes matched. Across containers, the only observed difference was the generated container hostname embedded in the ERROR token; the fixture retains both raw forms. The comparator excludes that hostname and the containing ERROR token's raw bytes from the cross-container equality check, while retaining all other token bytes and semantic error fields.

`node scripts/capture-rpc-output-wire.mjs` reproduces the two-container capture and compares stable observations with the retained fixture. `--write-fixture` creates a missing fixture and refuses to overwrite one. Run on a Docker host with Node dependencies; the original runs used `linux.local`. The script attaches to tedious's decrypted post-login TDS stream only after authentication succeeds, bounds packet and token lengths, and rejects unexpected tokens. It never records LOGIN7, TLS handshake data or credentials. Each response retains packet payload hex, token offsets, exact token hex, parsed fields and the callback outcome. The source values are fixed test data, including one isolated high surrogate and one 8,202-byte MAX value.

The raw wire establishes details hidden by tedious's `returnValue` event:

- Successful `sp_executesql` SET cases emit `DONEINPROC`, `RETURNSTATUS(0)`, `RETURNVALUE`, `DONEPROC` in that order. A nonzero-return user procedure emits `RETURNSTATUS(7)`, `RETURNVALUE`, `DONEPROC`. Tedious reports the return status with `doneProc`, so its event order alone cannot place the `RETURNSTATUS` token.
- The application output's `RETURNVALUE` has ordinal 2 because the RPC's statement and declaration parameters precede it. The user-procedure output has ordinal 0. Both names include `@` on the wire (`@p`). The status byte is 1, user type 0 and flags 0, including for a NULL output. The nullable INT example's full token is `ac02000240007000010000000000002604042a000000`.
- `NVARCHAR(4)` has TYPE_INFO `e708000904d00034`: eight declared bytes and the captured SQL Server collation. NULL uses `ffff` after TYPE_INFO; an isolated high surrogate followed by `Z` uses `040000d85a00`. `DECIMAL(9,2)` has TYPE_INFO `6a110902` (17-byte declared storage), while the non-null value uses five payload bytes `050115cd5b07`. Runtime values do not determine these declarations.
- The 4,101-unit NVARCHAR(MAX) result has TYPE_INFO `e7ffff0904d00034`, total PLP byte length 8,202 and three SQL Server chunks of 4,035, 4,084 and 83 bytes. The full raw units are retained. Chunk splitting is a wire observation; a different valid PLP partition still needs real-client verification.
- Mixed outputs declared as `@first NVARCHAR(MAX)`, `@middle INT`, `@last VARBINARY(MAX)` return in order `@middle` (original ordinal 3), `@first` (ordinal 2), `@last` (ordinal 4). The two MAX values are only one character/byte each, so grouping follows the declared large-object type rather than runtime payload length; order within the MAX group stays stable.
- An uncaught `THROW` after assignment emits `DONEINPROC`, `ERROR`, `DONEPROC` and no `RETURNSTATUS` or application `RETURNVALUE`. The ERROR includes the container hostname, which explains why raw bytes differ across otherwise identical containers.
- The `sp_prepare` handle has ordinal 0, wire name `@handle`, flags 0, TYPE_INFO `2604`, and follows `RETURNSTATUS(0)`. Its full token is `ac0000074000680061006e0064006c0065000100000000000026040401000000`. The existing `return_handle` helper strips `@` and emits flags 1, preserving a prior vector that this first-party SQL Server capture now contradicts. Correcting that helper and its tests requires a successor task under its active file claim.

The token structure follows the local [MS-TDS skill](../.agents/skills/tds-protocol/tokens.md) and Microsoft's [RETURNVALUE definition](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tds/7091f6f6-b83d-4ed2-afeb-ba5013dfb18f). The mixed case confirms the specification's large-object grouping for these MAX character/binary declarations; other large-object families remain untested. This capture does not prove msduck application OUTPUT execution, other data families, other SQL Server versions or full byte-for-byte compatibility. Root integration must bind directions, retain final variable values, suppress output on uncaught errors and emit `RETURNSTATUS` before the captured `RETURNVALUE` tokens and final `DONEPROC`.
