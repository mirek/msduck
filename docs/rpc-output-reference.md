# SQL Server RPC OUTPUT parameter evidence

`reference/rpc-output.json` records 23 first-party tedious RPC scenarios against the pinned SQL Server 2025 image (`scripts/lib/reference-container.mjs`). The generator ran each scenario sequence in two fresh databases, and the complete captures matched. Each request retains ordered `columnMetadata`, `row`, `doneInProc`, `returnValue`, `doneProc`, INFO/ERROR and callback observations. The fixture also retains the server version/collation query, setup response, input declarations and values. A successful capture proves reference behavior only; msduck still rejects ordinary application OUTPUT parameters in `src/rpc.rs`.

Run `node scripts/capture-rpc-output.mjs` on a host with Docker and Node dependencies to compare a fresh two-database capture with the retained fixture. `--write-fixture` creates a new fixture only when none exists and refuses to overwrite one. The owner generated this fixture on `linux.local` with the pinned image; the container helper generates credentials in memory, publishes a random loopback port and deletes only its own container. No credential is retained.

Observed rules relevant to implementation:

- For `sp_executesql`, SQL Server emits statement results and `DONEINPROC` events before application `RETURNVALUE` events, then `DONEPROC`. Two outputs are returned in RPC parameter order (`z`, then `a` in the captured case), even when the SELECT lists `a` first. `doneProc` exposes return status 0 in successful cases.
- The `RETURNVALUE` metadata reflects declarations even when the final value is NULL: `INT` uses `IntN(4)`, `BIGINT` `IntN(8)`, `BIT` `BitN(1)`, `NVARCHAR(4)` advertises eight bytes, `VARCHAR(4)` and `VARBINARY(4)` four bytes, and `DECIMAL(9,2)` advertises `DecimalN` with precision 9, scale 2 and length 17 in this capture. Do not infer output metadata from the runtime value or choose decimal storage length solely from precision.
- Empty Unicode text and empty binary values are distinct from NULL. An isolated high surrogate followed by `Z` survives the output path as raw UTF-16. An 8,192-code-unit `NVARCHAR(MAX)` output and an 8,193-byte `VARBINARY(MAX)` output retain their values and advertise max length 65,535; the JSON fixture preserves the full data.
- With `SET NOCOUNT ON`, successful statement completions visible to tedious change, while the `RETURNVALUE` and `DONEPROC` remain. `PRINT` appears as `infoMessage` before the final result. An uncaught `THROW` before or after assignment emits an ERROR and `DONEPROC`, with no application `RETURNVALUE`. The caught-error case emits the assigned output after its result and completion events.
- The captured user procedure returns its output before `DONEPROC` with status 7. A prepared `sp_prepare`/`sp_execute` sequence returns output values 4 and 10 on successive executions, but this tedious version reports `Unexpected output parameter p from sp_prepare` in both execution callbacks after receiving those values. The fixture retains both the server events and that client-level interpretation; a server implementation should not erase the difference to obtain a passing client test.

Tedious exposes output type metadata but strips leading `@` from output names and does not expose RETURNVALUE ordinal, status byte or raw token bytes in these events. `doneProc` exposes the parsed return status rather than a separate RETURNSTATUS event. Wire-level ordinal/status/TYPE_INFO bytes and behavior with other clients remain unproven here; capture them separately before claiming exact wire parity. This task does not integrate root RPC binding, execution or response emission. That follow-up must keep parameter declarations explicit, propagate final values only on the captured paths, preserve event order and handle error cleanup and prepared-driver behavior without guessing from the owner-local mssqlite model.
