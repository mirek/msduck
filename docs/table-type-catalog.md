# Table-type catalog foundation

The pinned SQL Server 2025 image (`mcr.microsoft.com/mssql/server:2025-latest@sha256:86cc6144ef39bb0fbed2329e1ad79b13ee82e7b2e4739213a0db0800e668a74a`, product version `17.0.4065.4`) was queried through Tedious 20 in four fresh databases across two independent containers. [`reference/table-type-catalog.json`](../reference/table-type-catalog.json) retains the complete setup/query responses: result column descriptors, rows, errors, INFO and DONE events. All four raw runs matched, including generated IDs, and an independent four-database replay matched the retained fixture. Reproduce with `node scripts/capture-table-type-catalog.mjs`; `--write-fixture` refuses an existing fixture.

Two types with the same name were created in `dbo` and `app`, each with `INT NOT NULL`, `NVARCHAR(12) NULL` and `VARBINARY(5) NULL` columns. `sys.types` returned separate rows with `system_type_id=243`, `user_type_id=257/258`, their respective user schema IDs, `max_length=-1`, `is_nullable=0`, `is_user_defined=1`, and `is_table_type=1`. `sys.table_types` inherits those columns and adds `type_table_object_id` plus `is_memory_optimized=0`. These observations agree with [Microsoft's catalog definition](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-table-types-transact-sql?view=sql-server-ver17).

Each `type_table_object_id` refers to a `sys.objects` row in the **sys** schema with type `TT`, description `TYPE_TABLE`, `is_ms_shipped=1`, and a generated name `TT_CatalogProbe_<eight-digit uppercase object-ID hex>`. Its `sys.columns` rows contain the table-type fields. `TYPE_ID('dbo.CatalogProbe')` and `TYPE_ID('app.CatalogProbe')` return the distinct user type IDs; `OBJECT_ID('dbo.CatalogProbe','TT')` and the `app` equivalent return NULL. `OBJECT_NAME(type_table_object_id)` returns the generated backing name, and `COL_NAME(type_table_object_id,2)` returns `label`. A table type is therefore not a normal user table object under its declared schema.

The root catalog now stores the type identity and backing columns transactionally in the DuckDB database. `type_catalog::create_table_type` derives scalar column metadata from parsed declarations and existing built-in catalog rows; it rejects unsupported declarations, missing schemas, duplicate type/column names, invalid lengths and unknown collations before writing. Its companion drop function removes the columns and type together. Both can run in a caller-owned transaction or own a transaction. Unit tests cover the retained catalog shape, ordinary-table coexistence, rollback, duplicate detection, deletion and reopen.

The reference also rejected `CREATE TYPE dbo.[int]` with error 219/state 1 despite its `dbo` qualification, a `DECIMAL(2,3)` column with error 183/state 1, duplicate `[Ä]`/`[ä]` columns with error 2705/state 3, `FLOAT(0)` with error 1001/state 1, and `FLOAT(54)` with error 2750/state 1. The catalog API rejects all five before writing. A lowercase `latin1_general_100_ci_as` declaration is accepted by SQL Server, while `sys.columns.collation_name` returns `Latin1_General_100_CI_AS`; the API now stores the canonical name for supported collations. Its Unicode lowercase duplicate check covers the observed case pair; full SQL Server identifier-collation equivalence remains an open compatibility gap. The ordinary-column join is restricted to `sys` built-ins so table-type rows cannot duplicate scalar columns. This is a catalog foundation, not a live `CREATE TYPE` or TVP execution path. The SQL batch parser/executor does not call the new API; the RPC dispatcher does not bind decoded TVP cells to declared table types or user procedures. Constraints, indexes, computed/default columns, memory-optimized table types, dependency checks on DROP and schema removal, table-type permissions, and complete TDS descriptor parity are also pending. The existing `TYPE_ID` helper resolves built-in unqualified names under `sys`; unqualified user-type lookup needs a later resolver change. Numeric object IDs here are server-owned identities and are not asserted equal to SQL Server's IDs; their relationships and stored metadata are the compatibility contract.
